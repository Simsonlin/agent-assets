# AI 输出的理解与核查

建立：2026-10-03。已提炼自写 Skill `personal/explain-for-understanding` 首版；尚未在目标项目验证原生调用与理解效果。外部 Skill 仅作阅读参考，未接入。

## 关注的问题

当 Agent 承担更多工作，人需要理解和检查它的结果。如何降低阅读负担，让结论、机制、条件与证据更容易辨认？什么时候清晰文字已经足够，什么时候值得临时制作图示、交互页面或视频？

主题覆盖写作约束、表达形式和解释产物。当前建议先服务人对结果的理解与核查，兼顾中文与英文；英文工具描述和 Agent 间指令的消歧可作为相邻方向。这个优先次序是设计建议，尚无实践效果支持。

### Karpathy 原帖的主线

以下是原帖观点的概括，不是本主题已验证的结论：

- 对文字，尝试要求模型使用 ASD-STE100，或放宽为“80% of the way to ASD-STE100”。这是提示方式，没有定义可测量的 80% 合规指标。
- 对结构与机制，尝试生成图示或图像；对适合探索的内容，尝试 HTML 页面、动画和交互。
- 对任意主题的定制讲解视频，他最看好；举例是程序化讲解动画配旁白，使用 ElevenLabs 或寻找本地替代方案。
- 随着智能和代码更容易获得，为一个具体问题制作大型、定制、可丢弃的解释产物可能变得划算。

原帖提供使用经验与尝试方向，没有给出这些形式改善理解的比较实验。文章中的 TeX/PDF、回看十段对话并提炼个人规则，以及 Shazam 视频实测等，属于文章引述的延伸线索；相关评论原文与视频效果未完整核查。

### 开源 Skill 的参考价值与问题

该 Skill 面向英文消歧，区分 Strict 与 STE-flavored 模式。后者放宽词汇约束，但仍保留较强的句长、语态和时态规则；不能据此把它等同于 Karpathy 的“80%”。它没有内置完整官方词典，也不保证完整 STE 合规。[主 Skill](https://github.com/danyuchn/asd-ste100-skill/blob/7d4a135a199a5d7447c4886bcd7ffe742a627bc9/SKILL.md)

值得借鉴的是先理解含义，再改写，并保护条件、范围和不确定性。但示例存在与这些原则冲突的改写：README 示例把“无供应商锁定”改成“不向外部存储数据”，新增了原文没有的承诺；Agent 指令示例把建议改成命令，还补了检查步骤。后者标出了新增内容，仍说明纯改写与提出改进建议需要分开表达。[示例](https://github.com/danyuchn/asd-ste100-skill/blob/7d4a135a199a5d7447c4886bcd7ffe742a627bc9/examples/before-after.md)

脚本是正则启发式检查，统一使用 25 词阈值，未自动区分 20 词的程序性指令上限；还将 check、verify、confirm、validate 归为同义词组。它不能判断这些词是否在项目中表示不同动作，也不比较改写前后的语义。适合作为检查线索，不能作为语义正确或 STE 合规的判定。[检查脚本](https://github.com/danyuchn/asd-ste100-skill/blob/7d4a135a199a5d7447c4886bcd7ffe742a627bc9/scripts/ste-lint.py)

## 当前方法建议

这一节是本次讨论形成、已用于首版 Skill 的方法，待通过实际材料观察和修订。

### 先确定读者需要理解或检查什么

先识别材料、读者任务和关键问题，再选择表达形式。以理解收益与制作成本判断是否需要更丰富的产物；不把原帖的形式顺序变成必须逐级升级的流程。

| 读者任务 | 优先考虑的形式 | 需要保留的内容 |
|---|---|---|
| 理解结论、执行操作 | 清晰文字、步骤表 | 动作主体、条件、顺序、例外 |
| 理解结构、流程或状态 | 图示 | 对象、关系、边界与关键状态 |
| 比较方案、探索参数变化 | 表格或交互 HTML | 假设、数值含义、适用范围 |
| 阅读公式与完整论证 | TeX/PDF | 符号定义、推导与来源 |
| 理解随时间展开的过程 | 动画或视频 | 关键状态、变化原因与讲解顺序 |

这张表是本主题的形式选择建议，其中 TeX/PDF 并非 Karpathy 原帖的直接建议。简单问题可以只用几句话；临时产物是否保留由用途决定，不自动纳入产品代码或长期维护范围。

### 清晰表达同时保护语义

- 同一个概念使用稳定名称；不同概念保留区别，不能机械合并近义词。
- 说明谁做什么、在什么条件下做；操作步骤一次表达一个主要动作。
- 保留数值、否定、例外与范围，保留“可能、必须、建议”的强度。
- 中文借鉴短句、明确主体和术语一致；不机械照搬英文词数、时态和批准词典规则，也不宣称中文文本符合 STE。
- 新增解释、假设或改进建议需要明确标出，避免悄悄改变原材料。
- 让文字、图示和交互内容可以回查依据；检查产物能否正常呈现，交互是否符合所解释的机制。

本仓库中的“暂存、安装、宿主发现、实际调用、产生效果”是五种不同事实。表达规则应帮助读者分辨它们；文字更顺、图更漂亮或页面能运行，都不能替代内容与证据的核查。

## 已提炼的工具与后续方向

`personal/explain-for-understanding` 已形成可按需选用的自写 Skill。输入可以是问题、现有材料或 Agent 的工作结果；识别读者任务与关键问题，核对依据，选择形式，生成解释，检查语义与呈现，最后给读者阅读和核查入口。

首版跨领域使用，无需先确定代码、数学或其他问题类型。深度与形式从请求和上下文判断，只在缺失信息会明显改变解释时询问。清晰文字与必要图示是基础；HTML、TeX/PDF 和视频按用户需要、理解收益、制作成本与可用工具选择。首版包含这些产物的条件性制作指导，没有绑定生成服务、内置渲染实现或效果保证。

源码位于常规 `skills/`，身份与状态由 catalog 登记；自写工具不需要经过外部来源的 staging。当前登记为 available，正式长期纳入仍由用户决定。学习主题记录成熟度、设计理由和实践反馈，不在 Skill 中放主题反向链接或依赖。

项目启用沿用 [按需启用流程](../../workflows/project-skills.md)。初期实践建议显式调用，方便分辨是否实际使用；首版保留宿主默认的调用可见性，按需安装与限制模型主动调用是两个不同选择。本次没有全局安装或给实际项目启用。

英文 STE 改写与上游 linter 可独立作为候选能力。若需要接入，按仓库来源流程保留原版；若需要个人特化，记录来源版本与改动理由。此主题保存理由和实践反馈，执行必需的规则与资源归完整资产目录，不让资产运行依赖主题文件。

## 下一次可尝试的内容

从一份真实的长技术解释、多步骤说明或 Agent 工作结果中，选一个读者确实感到难理解的例子。先比较原材料与清晰文字版本；只有结构或参数关系需要时，再尝试图示或交互页面。

观察三个问题：是否更容易理解，是否更容易检查，是否改变原意。留下具体例子、用户反馈、使用的方法或资产版本和证据入口；一次尝试不足以证明稳定增益。短反馈写在此页，需要独立回查时再拆到 `practice/`。

后续重点观察：跨领域默认解释是否合适，中文表达是否自然且保真，形式选择是否带来额外负担，新工具相对普通提示是否有可观察的帮助。具体实践与项目启用随后续任务目标推进，不由此页自动启动。
