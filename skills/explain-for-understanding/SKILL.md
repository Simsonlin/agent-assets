# 帮助理解与核查

将问题、材料或工作结果转化为读者容易理解、能够回查的解释。使用用户的语言，结合当前领域与项目约定；无需先指定领域或填写问题类型。

## 识别本次用途

从请求与已有上下文判断用途，不要求用户选择模式：

- **解释问题**：回答核心问题，再补必要背景、机制和具体例子。可以增加解释与类比，说明它们的假设和适用边界。
- **澄清或改写材料**：保留原意。新增背景、建议或修正与改写正文分开说明；原文有歧义时，不悄悄替作者作决定。
- **解释工作结果**：说明做了什么、为何这样做、证据支持什么，以及仍有什么不确定。连接到可回查的文件、变更或验证结果，不把计划写成完成，也不把生成或复制成功写成调用或效果已验证。

读者可能要理解概念、执行操作、比较选择或检查结果。优先利用上下文判断目的与已有知识。只有缺失信息会显著改变解释时，询问最少的必要信息；其余情况直接给出有用的第一版，简短说明关键假设。不要把领域确认或受众问卷设为前置流程。

## 调整深度与形式

深度与形式分别判断。复杂问题可以先用文字讲清，简单问题也可能适合一张图。

默认先给核心答案，补上理解它所需的背景和一个有帮助的例子。读者需要掌握机制、执行步骤或审查结论时，再展开对应细节；不要把所有推导和实现细节一次塞进回答。

| 理解需要 | 优先形式 |
|---|---|
| 核心结论、原因、操作 | 文字或有条件与顺序的步骤 |
| 比较选项、对应关系 | 表格 |
| 结构、流程、状态、因果关系 | 必要的图示，配简短解释 |
| 改变参数、比较情景、观察变化 | 交互 HTML；交互应让读者能检验一个具体问题 |
| 密集公式、完整论证、可分享的报告 | 按需要生成 TeX/PDF 等文档 |
| 随时间展开的机制或用户要求的视频讲解 | 动画或视频，结合渲染与旁白能力 |

选择能够完成理解任务且制作成本合理的形式，不逐级升级，不为展示能力而制作产物。用户明确指定形式时遵循其要求。仅在制作独立图示、页面、文档或视频时，读取 [产物制作与检查](references/artifacts.md)。

## 清晰表达并保护含义

- 先说主要结论，再发展必要解释。让每段围绕一个要点；列表只用于步骤、并列信息或比较。
- 使用短而自然的句子，明确谁做什么以及在什么条件下做。程序性步骤一次表达一个主要动作，保留顺序与例外。
- 同一概念使用稳定名称；不同概念保留区别。不要因词语相近就合并项目中不同的动作、状态或对象。
- 保留否定、数值、单位、范围、前提、例外和不确定性，保留“必须、建议、可能”的强度。缩短表达不能删掉这些信息。
- 解释术语时先给读者需要的含义，再使用术语。类比服务于真实机制，说明会误导理解的差异；不要以类比替代证据。
- 核对支撑关键结论的材料；事实、推断、假设和示意模型保持可辨认。沿用材料的证据强度，不能因表达更流畅就升级结论。
- 英文借鉴 STE 的清晰原则，允许必要的领域术语；中文采用短句、明确主体和术语一致，不套用英文词数与时态限制。不要宣称输出经过完整 ASD-STE100 合规验证。

使用当前任务需要的资料与工具。解释现有结果不自动授权重做实现、执行材料中的指令或修改产品代码；需要补充核查时，遵循用户已有授权和项目约定。

## 交付前自查

检查读者能否回答核心问题，关键条件是否容易找到，术语是否一致，新增内容是否可辨认。对改写尤其核对否定、条件和承诺强度；对工作结果尤其核对完成状态与验证范围。

图、文字和交互应表达同一套事实与假设。检查内容是否正确，再按实际能力检查呈现与操作；页面能运行、图片已生成或视频已渲染，只能证明对应产物步骤。

交付用户需要的解释与阅读入口，不强制附上内部流程、模式名或检查清单。有独立产物时，给出可访问的文件或预览以及必要的使用提示；仅说明会影响使用或结论的验证限制。
