# Agent 选择与采用 SDD

本指南规定 Agent 在新项目或现有项目中如何读取标准、与人讨论方案并最小落地。它是 `standard.yaml` 登记的 Agent 入口。

## 1. 先读取标准

Agent 必须完整读取 `standard.yaml` 的 `agent.requiredReads`，再按所选 Profile 和模块读取对应模板。不要要求用户逐份重复指定这些文件。

如果只能访问单个页面，先读取根 `README.md`，再沿其中链接读取本指南和必需参考。无法读取必要文件时，应说明缺失内容，不能假装已经按标准完成选择。

## 2. 只读检查项目事实

在讨论方案前，先进行不会改变项目状态的检查：

- Git 工作树及用户已有变更；
- 现有 README、规范、设计、ADR、Contract、测试和发布文档；
- 代码中的运行边界、独立消费者、持久化格式和兼容承诺；
- 当前项目是一次性 change、持续演进系统，还是受发布治理约束的产品；
- 人工验证、自动验证和实施/发布授权分别由谁负责。

新项目没有代码可检查时，以用户描述和已确认的项目计划为事实来源，并明确标出假设。

## 3. 讨论会改变选择的最少问题

优先从项目中发现答案，只询问无法确定且会改变方案的问题：

1. 是否需要长期维护“系统当前做什么”的 capability spec？
2. 是否存在独立消费者、跨 iframe/worker/进程/网络/仓库边界，或持久化格式？
3. 是否已有正式兼容承诺、多个独立消费者、发布门禁、审计或 fail-closed 要求？
4. 哪些架构或范围取舍需要多年保留理由，或未来很可能被反复追问？
5. 哪些验收必须由人完成？验证通过是否与实施、发布授权分开？
6. 现有文档是迁移、保留为辅助材料，还是已经形成重复真相？

不要把模板措辞、目录偏好或不影响结果的小问题都抛给用户。可以提出带假设的推荐，让用户修正。

## 4. 给出一个可确认的推荐

写项目文件前，Agent 必须先输出：

```text
推荐 Profile：quick-change | living-spec | governed-delivery
Persistence：spec-first | spec-anchored
Modules：adr、contract-first 或 none

选择理由：项目事实 → 选择条件
最小产物：本次必须创建或维护什么
条件产物：什么条件命中，因此创建什么
明确不创建：没有命中条件的目录或文件
权威边界：Spec、Contract、Decision、实现和验证分别以什么为准
Overrides/Core deviations：none，或风险与退出条件
重新评估条件：什么事实变化时重新讨论
待确认假设：仍需人类决定的事项
```

推荐规则：

- 默认 Living Spec；只有明确短期且不需要长期当前 Spec 时选择 Quick。
- 正式兼容、多个独立消费者、发布门禁或审计要求命中时选择 Governed。
- 独立消费者、跨运行边界、持久化格式或兼容承诺命中任一项，Contract-First 为强制模块。
- ADR 只用于重要、长期、难撤销或会反复被追问的决策。
- 项目可以选择偏离建议，但违反核心不变量必须登记 `core deviation`，不能伪装成普通 override。

## 5. 等待人类确认

人类明确确认 Profile、Persistence 和 Modules 前，不得创建、迁移或删除项目文件。用户只要求分析、比较或建议时，交付推荐即可。

确认只授权 SDD 采用范围，不自动授权功能实现、运行逻辑修改、发布、push 或外部操作。

## 6. 最小落地

确认后按 [采用指南](./adopt-sdd.md) 执行：

1. 保留用户已有变更；
2. 创建 `sdd/adoption.md`，记录标准来源地址、revision、版本、选择、理由、映射、调整和重新评估条件；
3. 只复制所选 Profile 的必需模板和已命中模块/条件模板；
4. 每个 change 显式声明 `specImpact` 和 `contractImpact`；
5. Spec 记录当前 WHAT，Contract 记录机器边界，ADR 记录 WHY，验证记录证据；
6. 优先复用现有 schema、IDL 或类型作为 Contract 权威，不创建等价副本；
7. 现有项目只迁移仍有价值的历史，不机械复制旧文档；
8. 新项目不得把目标行为伪装成已实现的当前事实。未实现行为留在 proposal/spec delta；当前 spec 可以保持 draft；
9. 不创建空目录或空的条件产物。

标准应作为采用时的快照被项目使用；中央标准更新不会静默覆盖项目已记录的 overrides。

## 7. 检查与交付

Agent 至少检查：

- `sdd/adoption.md` 与实际目录、Profile 和模块一致；
- 同一事实没有在 Spec、Contract、文档和测试间形成重复权威；
- 所有 change 都声明两个 impact；
- 条件产物判断与实际文件一致；
- 相对链接可达，旧策略没有继续作为第二套现行规则；
- 未把验证结果写成实施或发布授权；
- Git diff 没有混入采用范围之外的运行逻辑变化。

交付时报告推荐与最终选择、创建/迁移/删除的产物、保留的风险、验证结果和下一次重新评估条件。
