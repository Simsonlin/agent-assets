# 背景与方案推导

这套标准最初来自一次真实的合同换代事故，但首版已经从单一项目的“五层架构规范”调整为可按风险选择的 SDD Playbook。

## 起源：一次 v2 → v3 cutover

一个长期演进项目在正式切换合同时，运行时主流程已经通过，但发布阶段连续暴露旧版本残留：打包白名单、版本约束、按历史 spec 编号组织的验收脚本、旧字段断言和已删除文件引用。每修复一个检查，下一个过期检查才出现。

问题不在某一条断言，而在组织方式：

1. 同一个接口事实同时存在于文档、运行时代码、多个测试和 release gate。
2. 验收按“哪份历史 spec 创建了它”组织，而不是按当前能力或合同组织。
3. 旧合同和旧检查没有结构化退休机制。
4. 文档卫生、机制验证和发布授权被混成同一个 PASS/FAIL。

## 原规范解决了什么

最初方案强调：

- 合同事实保持单一权威；
- schema、类型或协议成为机器边界来源；
- 已发布合同冻结并版本化；
- 验证按当前合同和能力组织；
- 归档检查默认不参与发布；
- 验证通过与发布授权分离。

这些原则对正式合同换代有效，但原文把一种高治理项目结构写成了所有项目的默认答案，并将 `specs/` 限定为只记录 WHY。它还硬编码了事故项目的运行目录、强制合同版本目录、`CURRENT` 指针和 gate manifest。这会让普通修复、探索项目和仅需 Living Spec 的项目承担不必要成本。

## 为什么改成选择式 Playbook

外部成熟实践呈现的共同点不是某一种目录，而是根据问题选择持久化与治理强度：

- 短期变更可以 spec-first，完成后归档；
- 长期系统需要 spec-anchored，让当前 Spec 持续代表当前行为；
- 稳定机器接口需要独立 Contract；
- 正式兼容和发布场景才需要冻结版本、验证计划和 release decision；
- 重要长期决策适合独立 ADR；
- 教程、操作指南、参考和原理说明应分开，减少入口混乱。

因此当前版本提供 Quick Change、Living Spec 和 Governed Delivery 三个 Profile，并将 ADR、Contract-First 作为按条件启用的模块。

## Spec 与 Contract 的边界

当前 Spec 描述系统可观察行为的 WHAT；Contract 描述消费者可依赖的机器边界；Decision 解释 WHY；实现保留 HOW；Verification 保存证据。

Profile 解决产物持久化与治理问题，但不能单独表达一次 change 是快速验证、普通交付还是高保障实现。因此 Execution Intent 作为正交轴加入：Probe、Delivery、Assurance 分别改变证据与复核强度，不复制 Profile 的职责。

这修正了原规则“Spec 只讲 WHY”的过度限制。没有机器边界的能力仍然需要清晰 Spec；存在机器边界时，Spec 引用 Contract 而不复制协议正文。

测试默认只是证据。只有项目明确声明且人类可读的 executable spec/contract，才可以同时承担权威与验证角色。

## 保留的可靠原则

- 单一权威来源；
- 合同按真实边界触发，而不是所有项目强制创建；
- 已发布合同不可原地覆盖；
- 过期内容归档而不是删除或继续默认运行；
- 人类实施授权、验证结论和发布授权相互独立；
- 项目可以渐进采用和调整，但关键偏离必须可见。

## 当前局限

- 当前版本提供 Agent 引导、人工确认与模板复制，但没有自动验证或升级工具。
- 模板和迁移规则已通过第一个真实项目 `html-to-design-penpot` 验证；精简结果保存在 `examples/`。
- `spec-execution` Skill 可以消费本标准的 change 语义，但仍是独立工程资产；Multi-repo 和 Compliance Traceability 留待实际需求出现后设计，使用本标准不依赖安装 Skill。
- 本标准不是认证体系；`core deviation` 的目标是暴露风险，不是阻止项目作出有意识的选择。
